# Реализация хеш-таблиц на C

[[Алгоритмы и C]]

Для словаря недостаточно хранить только значения: при коллизиях нужно отличать исходные ключи. Представление пары, состояние ячейки и владение памятью определяют корректность вставки, поиска и удаления. Ниже сохранена логика лекций 7–8; фрагменты с пропусками остаются учебными схемами, а не готовой библиотекой.

## Пара ключ-значение и const

В начале лекции 8 корзины хранят отдельные числа, затем в них появляются пары `4:2`, `8:4`: слева ключ, справа значение. Хеш даёт номер корзины, а сравнение ключей выбирает правильную пару в ней.

Исходное объявление:

```c
typedef struct {
    const void *key;
    const void *value;
} GenericPair;
```

Это два указателя на объекты. `const void *` запрещает изменять объект **через данный указатель**, но сам указатель-поле можно переназначить. Это не делает вложенные объекты глубоко неизменяемыми и не создаёт их копий. Вариант `void * const key` запрещал бы менять сам указатель.

В слайде также показан `struct Point { const int x; const int y; };`: его поля нельзя присваивать после инициализации. **Уточнение источника:** кортеж — упорядоченный набор; неизменяемость зависит от конкретного типа и языка. Структура C не становится неизменяемой только из-за названия «кортеж». `const` существовал уже в C90; подпись «начиная с C99» ошибочна.

Объявление первой таблицы в лекции содержит `Vector *values`, `const size_t key_size`, `const size_t val_size`, `const size_t capacity`. Следующий слайд присваивает `table->key_size = key_size` после `malloc`: это противоречит `const` у поля. Изменяемая при рехешировании `capacity` тоже не может быть таким полем. Полная инициализация и управление ошибками в источнике опущены.

## Три способа хранить пары

![[Пара ключ-значение — три представления.png]]

Рисунок сравнивает массив структур с указателями, сплошные байты ключей и значений и массив указателей на отдельно выделенные пары. Стрелки означают переход к другому объекту памяти, полосы — расположенные подряд байты. Для примера на рисунке ключ занимает 1 байт, значение — 2.

| Представление | Размер одного элемента массива | Где ключ и значение |
|---|---|---|
| `GenericPair` | `sizeof(GenericPair)` | Указатели внутри структуры ведут к данным |
| Упакованная пара байтов | `key_size + val_size` | Ключ с начала, значение после ключа |
| Указатель на пару | `sizeof(void *)` либо размер конкретного указателя | В отдельном блоке |

Показанные вызовы имеют разный смысл:

```c
createVectorBySize(TABLE_MIN_SIZE, sizeof(GenericPair));
/* В слайде ошибочно: sizeof(key_size + val_size) */
createVectorBySize(TABLE_MIN_SIZE, key_size + val_size);
/* Для массива указателей вместо sizeof(sizeof(long long)): */
createVectorBySize(TABLE_MIN_SIZE, sizeof(void *));
```

**Уточнение:** `sizeof(key_size + val_size)` возвращает размер типа выражения, обычно `sizeof(size_t)`, а не сумму двух переданных размеров. `sizeof(sizeof(long long))` также даёт `sizeof(size_t)`; он не задаёт переносимый размер указателя. Само сложение размеров и произведение на вместимость должны помещаться в `size_t`.

Для упакованной пары:

```c
unsigned char *slot; /* адрес начала записи */
/* key_size байтов ключа начинаются с slot */
unsigned char *value = slot + key_size;
```

Арифметика над `void *` не является переносимым C; сначала нужен байтовый указатель. Скопировать `int` или `float` из смещённой позиции безопаснее через `memcpy` в правильно выровненную переменную: произвольное `slot + key_size` может не иметь требуемого выравнивания.

**Дополнительное пояснение к памяти:** если используется именно упакованная схема, полезные данные для $m$ записей занимают $m(key\_size+val\_size)$ байтов, отдельно нужны состояния ячеек и поля контейнера. Массив `GenericPair` резервирует только сами указатели, а не объекты по ним. В задании слайда о расчёте четырёх размеров нет готового теоретического решения; дополнительные ответы на это упражнение не добавляются.

## Создание таблицы и контракты

В открытой адресации `values` должен хранить $m$ доступных ячеек, размеры ключа и значения должны быть согласованы с выбранным представлением, а число живых записей начинается с нуля. Схема из лекции:

```text
выделить HashTable
создать Vector на TABLE_MIN_SIZE записей
сохранить key_size, val_size, size, capacity
вернуть таблицу
```

В исходнике стоят `...`, отсутствует полный контракт `createPairV2`, а часть полей не инициализируется явно. Поэтому тело не переносится как завершённая функция. **Дополнительное пояснение:** конструктор должен обработать отказ каждого выделения, освободить уже полученное и инициализировать состояния ячеек. Запрошенная вместимость и логическое число доступных ячеек в API `Vector` должны совпадать с тем, что проверяет `getVectorItem`.

В раннем эскизе цепочек лекции 7 сохраняется только `val_size`, корзина выделяется через `sizeof(long long)`, `hash(key)` не ограничивается вместимостью, а ключи вообще не сохраняются. Это промежуточный эскиз мотивации, не корректный обобщённый словарь. Размер указателя и запись структуры списка должны соответствовать реальному типу элемента вектора.

## Вставка при открытой адресации

Источник строит пару и исследует квадратичную последовательность:

```c
size_t index = hash(key) % table->capacity;
/* На слайде i называется counter: */
size_t probe = (index + i * i) % table->capacity;
```

Это формула, а не обещание безопасного машинного умножения при произвольном `i`. В исходнике используется `(int)pow(counter, 2)`, что добавляет вещественное вычисление и риск выхода за диапазон `int`.

Логика лекции: если ячейка пуста либо ключ совпадает, записать пару; иначе увеличить номер пробы; после вставки проверить необходимость роста. При совпадении ключа значение обновляется, число записей не увеличивается.

**Уточнённая учебная схема, раскрывающая удаление:**

```text
запомнить first_deleted = NONE
для ограниченного набора проб по выбранному правилу:
    если OCCUPIED и ключ совпал: заменить значение, закончить
    если DELETED и first_deleted ещё нет: запомнить позицию
    если EMPTY:
        вставить в first_deleted, если она была, иначе сюда
        увеличить число живых записей, закончить
если пробы исчерпаны:
    использовать сохранённую удалённую позицию, если корректность
    обхода гарантирует отсутствие дубликата; иначе пересобрать/сообщить отказ
```

`DELETED` не позволяет сразу завершить поиск совпадающего ключа: он может быть дальше. В слайде используются `while(counter >= 0)` и присваивание `counter=-100` для выхода. Это скрывает условие завершения. Нужны явные границы проб; квадратичная последовательность может зациклиться, даже если где-то есть свободное место.

Условие `*(char *)item == 0` в исходнике принимает первый байт ключа за признак пустоты. Тогда законный ключ с нулевым первым байтом нельзя отличить от пустой записи. Нужен отдельный тег состояния или заранее запрещённый ключевой код по явному контракту. `memcmp` сравнивает представление байтов; для структур с padding, разных представлений одного значения и строковых указателей это не обязательно смысловое равенство. Переданный `CmpFunc cmp` в исходном поиске игнорируется — его нужно согласовать с хешем: равные ключи должны иметь один хеш.

После `setVectorItem(..., pair)` источник делает `free(pair)`. Это допустимо лишь если вектор уже скопировал байты пары; при хранении указателя возник бы висячий адрес. При отказе вставки также нужно освободить временную пару.

## Поиск и удалённая метка

Поиск повторяет **ту же** последовательность проб:

```text
OCCUPIED + равный ключ → вернуть значение
OCCUPIED + другой ключ → следующая проба
DELETED → следующая проба
EMPTY → ключ отсутствует
исчерпание допустимых проб → отсутствие/ошибка заполнения по контракту
```

Источник возвращает `item + key_size`. В переносимом коде это `(unsigned char *)item + key_size`. Это адрес внутри таблицы: он может стать недействительным после рехеширования, удаления или перемещения буфера, поэтому контракт владения должен отличать его от выделенной копии.

![[Открытая адресация — удаление.png]]

Верхний ряд содержит цепочку проб через $2,3,4,5$. После удаления $3$ нельзя превратить его место в обычную пустую ячейку: поиск $4$ остановился бы раньше времени. Стрелка через удалённую позицию должна сохраниться логически.

Удаление сначала находит пару, копирует возвращаемое значение и помечает запись `DELETED`. На слайде выполнено:

```c
*(char *)pair = '\n';
void *value_return = malloc(table->val_size);
memcpy(value_return, pair + table->key_size, table->val_size);
return value_return;
```

**Уточнения:** `\n` — обычное значение байта, которое может встретиться в ключе; исходный поиск не содержит отдельной обработки этого маркера. Таким образом, фрагмент не реализует полноценные три состояния. Дополнительно необходимы проверка `malloc`, уменьшение числа живых записей и учёт удалённых мест при пересборке. Возвращённой независимо выделенной копией владеет вызывающий. Практически удобнее копировать результат до изменения состояния, чтобы отказ выделения не оставлял неожиданно удалённую запись.

## Метод цепочек с параллельными списками

Второй вариант лекции 8 содержит:

```c
typedef struct {
    Vector *keys;
    Vector *values;
    /* размеры, число записей, вместимость — опущены на слайде */
} HashTable;
```

В каждом векторе элемент имеет размер `sizeof(GenericList)`: это массив структур списков. В корзине $i$ список ключей и список значений имеют одинаковую длину; ключу в позиции $j$ соответствует значение в позиции $j$ другого списка.

**Инвариант:** добавление, замена и удаление должны сохранять это соответствие. Более прямой вариант с одним списком пар упоминается в лекции, но полная реализация не дана.

Вставка из источника:

```text
i = hash(key) % capacity
получить список ключей корзины i
если корзина ещё не создана: создать оба списка
a = findItem(keys[i], key, cmp)
если ключ отсутствует: добавить key и value в концы обоих списков
иначе: заменить записи в обоих списках на позиции a
проверить необходимость рехеширования
```

Источник копирует структуру `list_k` в вектор и вызывает `freeList(list_k)`. Корректность зависит от того, уничтожает ли `freeList` только оболочку или также узлы и данные; поверхностная копия головы не создаёт независимое владение узлами. Без точного контракта это нельзя считать безопасным. Отказ второй из двух вставок требует отката первой, иначе списки разъедутся.

Получение корзины в лекции проверяет `*((char *)pt + 8) == 0`. Смещение `8` предполагает конкретный размер указателя и раскладку структуры, а проверка одного байта `elem_size` не равносильна сравнению всего поля с нулём. Используют типизированный доступ к полям и явный признак созданной корзины; правило платформенного смещения нельзя превращать в переносимый API.

Поиск значения: получить корзину → найти индекс ключа → получить узел значения с таким индексом → вернуть `node->data`. Дополнительный проход по второму списку сохраняет линейность по длине корзины, но увеличивает работу.

Удаление: найти индекс → удалить ключ → удалить и вернуть значение с тем же индексом → при необходимости пересобрать. Если `popItem` возвращает выделенную копию ключа, её нельзя терять: на слайде `popItem(key_list, list_index)` игнорируется. Возврат значения и освобождение удалённого ключа должны соответствовать владению.

В интерфейсе списка прежних слайдов «не найдено» — `(unsigned int)-1`. Записать такой результат в `long` и проверить `<0` на типичной 64-битной платформе недостаточно: значение может остаться положительным `UINT_MAX`. Используют согласованный тип результата и маркер. Повторённый `findItem` с `break` после совпадения всё равно доходит до безусловного `return -1`; исправленный ранний возврат сохранён в [[Обобщённый связный список и функции сравнения]].

## Контракты рехеширования и ресурсов

Во всех вариантах после роста нужно заново размещать живые пары. Сохранить старые индексы нельзя; индекс зависит от новой вместимости. Меняется и положение возвращённых внутренних указателей.

**Дополнительное пояснение по состояниям:** различаются число живых записей, вместимость массива и количество удалённых меток. Память цепочек включает узлы, ключи и значения, а память открытой адресации — все $m$ слотов, включая пустые. Освобождение таблицы должно обходить только объекты, которыми она владеет. Недостающие тела `createPairV2`, расширения и полного освобождения не восстановлены как авторский код.

Теория и доказательства стоимости: [[Хеш-таблицы — функции, коллизии и оценки]].
