# Динамический массив, список и стоимость операций

> [!abstract] Суть
> Скорость операции определяется способом хранения данных. Массив вычисляет адрес по индексу, а список добирается до узла по связям.

## Динамический массив

Массив размещает элементы подряд. Адрес элемента с индексом $i$ вычисляется как начало буфера плюс $i$ размеров элемента, поэтому индексирование занимает $O(1)$.

Динамический массив отделяет `size` — число занятых элементов — от `capacity` — числа доступных мест. Пока есть запас, добавление в конец записывает один элемент. Когда запас заканчивается, выделяется больший буфер и переносятся старые элементы.

Если вместимость увеличивать геометрически, например удваивать, суммарное число переносов при $n$ добавлениях оценивается геометрической суммой $1+2+4+\dots<2n$. Все добавления вместе требуют $O(n)$ работы, поэтому на одно приходится амортизированное $O(1)$.

Это не означает, что каждый вызов быстр: отдельное расширение стоит $O(n)$. Амортизированная оценка относится к последовательности операций и не требует случайного распределения входов. Увеличение буфера на одно место при каждом добавлении может дать $O(n^2)$ суммарных переносов.

## Связный список

Узел односвязного списка содержит данные и указатель на следующий узел; двусвязного — ещё и на предыдущий. Узлы не обязаны располагаться рядом.

Поиск по индексу требует последовательного прохода. Изменение связей может быть постоянным по времени, если нужный узел и необходимые соседние связи уже известны. Если сначала надо найти позицию, стоимость поиска также учитывается.

| Операция | Динамический массив | Односвязный список |
|---|---|---|
| Доступ по индексу | $O(1)$ | $O(n)$ |
| Добавление в конец | Амортизированное $O(1)$ | $O(1)$ при наличии указателя на хвост |
| Удаление первого | $O(n)$ из-за сдвига | $O(1)$ |
| Удаление последнего | $O(1)$ без уменьшения буфера | $O(n)$ для поиска предшественника |
| Поиск значения без дополнительного индекса | $O(n)$ | $O(n)$ |

Для двусвязного списка с указателем на хвост удаление последнего узла занимает $O(1)$. За это платят дополнительными связями и памятью.

## Асимптотика и реальное выполнение

Обозначение $O(g(n))$ задаёт верхнюю оценку роста затрат с точностью до постоянного множителя при достаточно больших $n$. Оно не сообщает точное время в секундах.

Расположение подряд улучшает локальность: соседние элементы массива часто попадают в одну кэш-линию. Поэтому два алгоритма с одинаковой асимптотикой могут существенно различаться по скорости. Поэтому асимптотика не исчерпывает стоимость конкретного доступа к данным.

## Теория проверки корректности

Тест сопоставляет поведение программы с ожидаемым результатом на выбранных данных. Функциональные тесты проверяют основной смысл операций, граничные — переходы между случаями, стресс-тесты — поведение на больших объёмах.

Пройденные тесты не доказывают корректность на всех входах. Инвариант описывает свойство, которое должно сохраняться после каждой операции: например, $0\le size\le capacity$. Различие между тестом и инвариантом — различие между наблюдением отдельных выполнений и общим условием корректного состояния.

## Уточнённая таблица массива и двух видов списка

Оценки относятся к указанному представлению. Для $O(1)$ доступа к последнему элементу и добавления в конец списка нужен сохранённый хвост; исходный `GenericList`, хранящий только `head`, этого не обеспечивает.

| Операция | Динамический массив | Односвязный с head и tail | Двусвязный с head и tail |
|---|---|---|---|
| Получение/замена по индексу | $O(1)$ | $O(n)$ | $O(n)$ |
| Первый/последний | $O(1)$ | $O(1)$ | $O(1)$ |
| Добавление в конец | Амортизированно $O(1)$ | $O(1)$ | $O(1)$ |
| Удаление первого | $O(n)$ | $O(1)$ | $O(1)$ |
| Удаление последнего | $O(1)$ без сжатия, амортизированно $O(1)$ при подходящей политике | $O(n)$ | $O(1)$ |
| Удаление по индексу из середины | $O(n)$ | $O(n)$ с поиском | $O(n)$ с поиском |
| Поиск значения | $O(n)$ | $O(n)$ | $O(n)$ |

Если нужный узел и предшественник уже известны, удаление связи не требует повторного индексного поиска. $O(1)$ означает ограниченное число шагов относительно выбранного размера входа, а не одинаковое фактическое время на любых данных и устройствах. $O(n)$ — верхняя оценка роста, не точный закон «в десять раз элементов — ровно в десять раз секунд».

## Память представления

Массив занимает приблизительно `capacity * elem_size` плюс поля управления, а не обязательно `size * elem_size`. Для показанных 64-битных узлов с `void *data` и `next` узел односвязного списка занимает обычно 16 байт, с дополнительным `prev` — 24. Ещё нужны объект списка, отдельные данные и расходы аллокатора. Формулы `N*16+8` и `N*24+8` в PDF — неполный пример, не общая стоимость. В реальном `GenericList` есть также `elem_size`.

Пример выбора: температуры по номерам регионов удобно хранить в массиве ради индексирования. Для добавления задач в конец и удаления с обоих концов подходит двусвязный список с хвостом; односвязный без обратных ссылок удаляет последний за линейное время. Утверждение «список всегда тяжелее массива» слишком общее: расходы зависят от заполнения массива, размера данных и организации узлов.

## Зачем выделять контейнер

Без `Vector` код сглаживания отдельно хранит указатель результата и `size_out`, вручную увеличивает размер и вызывает `realloc` после каждого числа. Увеличение на одно место даёт потенциально квадратичные переносы; прямое присваивание результата `realloc` рискует утечкой при отказе. `Vector` объединяет данные, размер и вместимость, а добавление снаружи выглядит как `appendVectorItem(arr_out, &value)`.

Амортизированная оценка — стоимость всей последовательности операций, а не вероятностное «среднее по удачным входам». Для сжатия тоже нужна подходящая политика: неудачное уменьшение после каждого удаления может уничтожить преимущество геометрического запаса.

### Уточнение формул памяти из оригинальной презентации

В таблице лекции 6 для массива записано `N * sizeof(el) + 12 bytes`. Для показанного `Vector` с указателем и двумя `size_t` это не общая формула. В распространённой 64-битной среде сама структура занимает 24 байта; её буфер занимает `capacity * sizeof(el)`, а не обязательно `size * sizeof(el)`. У обобщённого вектора с дополнительным `elem_size` в той же модели поля занимают 32 байта. Это размеры представления без дополнительных расходов аллокатора.

Формулы слайда `N * 16 + 8` и `N * 24 + 8` для списков также не учитывают все варианты полей контейнера, отдельно размещённые данные и расходы выделения памяти. Оценку нужно строить по конкретному объявлению структуры, а не переносить фиксированную прибавку из таблицы на любой контейнер.

## Скрытые обходы за короткими выражениями

В начале лекции 5 показан фрагмент функции `do_smt`:

```python
array_unique = list(set(array))
dict_count = dict(map(lambda v: (v, array.count(v)), array_unique))
counts_list_unique = list(set(list(dict_count.values())))
```

Фрагмент сначала получает уникальные значения, затем для каждого считает число появлений в исходном списке и, наконец, оставляет разные значения частот. Дальнейшее тело функции на слайде отсутствует.

Короткая запись не устраняет обходы. Если во входе $n$ элементов и $k$ разных значений, вызов `array.count(v)` просматривает исходный список; повторение для $k$ значений даёт $O(nk)$ при постоянной стоимости сравнения. В случае $k=n$ получается квадратичный рост. Это разбор стоимости приведённого примера; [исходник `list_count_impl` CPython](https://github.com/python/cpython/blob/3.14/Objects/listobject.c) подтверждает последовательный обход.

Следующий слайд показывает цикл внутри `set_update_iterable_lock_held` из `setobject.c`: создание множества из итерируемого объекта должно получить его элементы и добавить их. Скрытый цикл объясняет работу по построению коллекции, но не доказывает линейный поиск каждого элемента в уже готовом множестве. Внутреннее устройство и цикл пробирования видны в [исходнике `setobject.c` CPython](https://github.com/python/cpython/blob/3.14/Objects/setobject.c). Здесь исправлено возможное обобщение слайда «внутри всё равно цикл»: нужно различать построение контейнера, полный обход и поиск в нём.

Промежуточные `list`, `set` и `dict` также требуют памяти. Этот пример объясняет роль алгоритма и представления данных; из него не следует, что любая программа на одном языке быстрее любой программы на другом.
