# Тестирование и корректность программ на C

> [!abstract] Суть
> Автоматический тест сопоставляет наблюдаемое поведение с ожидаемым. Выбор граничных данных помогает обнаружить ошибки контракта, точности, времени и управления памятью.

## Ручная проверка и assert

В примере калькулятора ручной ввод через `scanf("%hd %hd %c", &a, &b, &sym)` и вывод результата требуют проверки глазами. Запись аргументов прямо в программе упрощает повторение, но всё ещё не сравнивает результат автоматически. `assert` из `<assert.h>` проверяет условие: при ложном результате выдаётся диагностика и программа аварийно завершается; при истинном выполнение продолжается.

```c
#include <assert.h>

float calc(short a, short b, char symbol) {
    switch (symbol) {
        case '+': return (float)a + b;
        case '-': return (float)a - b;
        case '*': return (float)a * b;
        case '/': return b == 0 ? -1.0f : (float)a / b;
        default: return -1.0f;
    }
}

void calculator_examples(void) {
    assert(calc(2, 1, '+') == 3.0f);
    assert(calc(2, 1, '-') == 1.0f);
    assert(calc(3, 2, '*') == 6.0f);
    assert(calc(6, 2, '/') == 3.0f);
    assert(calc(1, 1, '@') == -1.0f);
    assert(calc(1, 1, '\0') == -1.0f);
    assert(calc(0, 0, '+') == 0.0f);
    assert(calc(0, 0, '-') == 0.0f);
    assert(calc(0, 0, '*') == 0.0f);
    assert(calc(0, 1, '/') == 0.0f);
    assert(calc(0, 0, '/') == -1.0f);
    assert(calc(1, 0, '/') == -1.0f);
}
```

В исходном калькуляторе проверка нулевого знаменателя отсутствовала; здесь она добавлена. До арифметики первый операнд приводится к `float`, поэтому пример не выполняет сначала умножение двух `short` как целых. Возврат −1 неоднозначен: `calc(1,2,'-')` даёт то же значение без ошибки. Ошибки и корректные результаты в таком интерфейсе смешаны.

При определённом `NDEBUG` проверки `assert` отключаются. Поэтому обязательные проверки входа и действия с побочными эффектами не следует оставлять только внутри `assert`.

## Назначение и виды тестов

Автоматические проверки экономят повторный ручной труд и обнаруживают регрессии после изменений. Повторяемость, изолированность и понятная причина сбоя помогают интерпретировать результат. При изменении требований тесты тоже требуют пересмотра; конечный набор успешных проверок не доказывает корректность всех входов.

| Масштаб | Объект проверки |
|---|---|
| Unit | Небольшая единица поведения, например функция или класс/модуль |
| Компонентный | Функциональный блок |
| Интеграционный | Взаимодействие блоков |
| End-to-End | Полный пользовательский сценарий |

Пирамида из PDF предполагает много мелких и меньше крупных проверок. Вызов нескольких функций внутри одного теста не делает его автоматически интеграционным: например, создание и заполнение `Vector` может быть подготовкой проверки той же единицы.

| Направление | Примеры из конспекта |
|---|---|
| Функциональное | Сортировка `[3,1,2]` в `[1,2,3]` |
| Граничное | Пустой массив, один элемент, ноль, крайние значения, `NULL` |
| Стресс | Миллион элементов, уже отсортированный вход, большие объёмы выделений |
| Производительность | Измерения на 1000, 100000, 10000000 элементах |

Точное ограничение скорости зависит от машины и условий, а не только от числа элементов. «Один тест — одна проверка» — упрощённая эвристика источника: важнее связная причина отказа и независимость тестов.

## Границы калькулятора и точность

Для показанного 16-битного `short` в PDF рассматриваются `32767+1`, `-32768-1`, `32767*32767`, а также `5/0`, `0/5`, `-10/5`, операции с нулями и неизвестными знаками. Математические ожидаемые значения первых трёх — 32768, −32769 и 1073676289.

В обычном binary32 последний результат не представим точно, поэтому проверка возвращённого `float` против точной константы `1073676289.0` обнаруживает потерю точности. Исходный пример действительно может падать; он не должен выдаваться за гарантированно успешный тест. `float` имеет обычно около семи значащих цифр, тогда как число содержит десять. Выбор типа результата и критерия сравнения должен соответствовать контракту.

## Подсчёт делителей: от перебора к парам

Первый алгоритм перебирает $i=1,\ldots,n$, увеличивая счётчик при `n % i == 0`: для положительного $n$ стоимость $O(n)$. Для отрицательного входа условие `i <= num` сразу ложно. При верхнем пределе `INT_MAX` простой цикл с `int i++` дополнительно рискует переполнить счётчик после последней итерации.

| Вход | Результат по контракту примера |
|---|---|
| 6 | 4: 1, 2, 3, 6 |
| 5 | 2 |
| 100 | 9 |
| −6 | 8: положительные и отрицательные делители |
| 0 | 0 — договорённость программы, не математическое число делителей нуля |
| 1 | 1 |
| 2147483647 | 2, если поддерживается такой `int`; число простое |

Контракт источника для положительного входа считает только положительные делители, для отрицательного — оба знака. Это асимметричное, но явно заданное поведение. У нуля математически бесконечно много ненулевых целых делителей.

Делители положительного $m$ образуют пары $d,m/d$; хотя бы один не больше $\sqrt m$. Для 100 пары — $(1,100)$, $(2,50)$, $(4,25)$, $(5,20)$, $(10,10)$. На пару прибавляется 2, на квадратный корень — 1. Получается $O(\sqrt m)$, около 46 тысяч шагов вместо двух миллиардов для приведённого простого числа. Четыре секунды и требование менее секунды в PDF относятся к конкретному запуску.

Исправленный вариант того же алгоритма не вычисляет `-INT_MIN` в `int` и не умножает большие `i*i`:

```c
#include <stdint.h>

int countDivisorsOfNumber(int num) {
    if (num == 0) return 0;
    uintmax_t magnitude = num < 0
        ? (uintmax_t)(-(intmax_t)(num + 1)) + 1
        : (uintmax_t)num;
    int count = 0;
    for (uintmax_t i = 1; i <= magnitude / i; ++i) {
        if (magnitude % i == 0) {
            count += i == magnitude / i ? 1 : 2;
        }
    }
    return num < 0 ? count * 2 : count;
}
```

Исходное `i*i == num` ошибочно для −100: квадрат сравнивается с отрицательным числом, поэтому парный корень считается дважды. Здесь сравнение производится для модуля. Простое `abs(num)` не было бы полным исправлением для минимального `int`. При показанном 32-битном `int` счётчик результата помещается в `int`; для иной разрядности диапазон результата тоже должен соответствовать контракту.

## Измерение времени

```c
#include <time.h>

int countDivisorsOfNumber(int num);

double divisor_cpu_seconds(int num) {
    clock_t start = clock();
    if (start == (clock_t)-1) return -1.0;
    (void)countDivisorsOfNumber(num);
    clock_t finish = clock();
    if (finish == (clock_t)-1) return -1.0;
    return (double)(finish - start) / CLOCKS_PER_SEC;
}
```

`clock()` измеряет процессорное время, не обязательно прошедшее настенное. В исходном тесте `assert(time_spent_s < 1.)` задаёт локальный порог; он не является универсальной гарантией алгоритма.

## Контракт операций Vector как предмет проверки

Источник разделяет `vector.h`, `vector.c`, `tests.c`. В конспекте теоретически важны состояния и границы операций, а не лабораторный чеклист:

| Операция | Условия и поведение, которые различаются |
|---|---|
| Создание | Пустое состояние, разные размеры элементов; нулевой размер должен иметь определённую обработку |
| Добавление | Переход через границу capacity, разные типы; нулевые указатели |
| Получение | Пустой контейнер, действительный и недействительный индекс; сохранение данных после роста и удаления |
| Замена | Изменение нужного элемента после изменения вместимости; крайние и недействительные индексы |
| Удаление | Изменение длины, порядка и владения возвращаемым объектом |

Типы примеров — `int`, `float`, `double`, `char`, `bool`, строки и `Vector *`. Обобщённый байтовый контейнер не умеет сам распознавать «не тот тип» за `void *`: это обязанность контракта вызывающей стороны. Для `size_t` отрицательный аргумент преобразуется в большое беззнаковое значение и должен отсекаться проверкой диапазона.

Инвариант $0\le size\le capacity$ описывает допустимое состояние после каждой операции и отличается от проверки отдельных запусков.
